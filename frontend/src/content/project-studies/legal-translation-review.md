> 외부 반출이 제한된 법률 문서를 자체 DB와 GPU 서버에서 추출·번역하고, 연구진이 원문과 결과를 대조 검수하는 시스템입니다.

해외 대학 연구실과의 공동 연구 과제로 개발했습니다. 한림대학교 지능형의사결정시스템 연구실 (LIT LAB).

## 담당 범위와 구현

- **프론트엔드 전체:** 문서 업로드부터 추출·번역 진행 상태, 블록별 검수, 수정과 재시도까지 연구진이 사용하는 화면을 설계·구현했습니다.
- **추출기 교체와 블록 검수:** 먼저 검토한 Marker-pdf는 문단 사이에 끼는 머리말·꼬리말을 안정적으로 구조화하기 어려웠고, 태깅·LLM 후처리는 시간이 오래 걸렸습니다. MinerU로 추출기를 교체하고 블록 위치 좌표를 이용해 원본 PDF↔추출문, 추출문↔번역문을 대조하도록 구현했습니다. 잘못 나뉜 블록은 다음 문단과 병합하고, 합쳐진 블록은 커서 위치에서 분리할 수 있게 했습니다.
- **번역 모델과 처리 상태:** TranslateGemma를 번역 모델로 선정·연결하고, 처리 진행률(%)을 화면에 실시간으로 표시했습니다. 추출·번역이 실패한 작업은 같은 화면에서 재시도할 수 있게 했습니다.
- **공용 GPU 작업 관리:** 예약 중인 GPU에 새 작업이 들어오면 실패시키지 않고 큐에서 기다리도록 설계했습니다. GPU 관리자 API를 화면에 연결해 예약·모델 상태를 주기적으로 표시했습니다.

시스템은 Gemma4로 문맥을 생성하고 TranslateGemma로 번역합니다. 아래는 추출·번역·검수·GPU 작업을 하나의 흐름에 연결한 방법입니다.

## 📌 왜 만들었나

공동 연구에 쓰는 판결문은 **비공개 문서라 외부 전송이 불가능**합니다. DeepL이나 Google 번역 같은 상용 API는 문서를 외부 서버로 보내기 때문에 애초에 선택지가 아니었습니다.

그렇다고 번역 품질을 포기할 수도 없었습니다. 법률 문서는 사건번호 하나, 금액 숫자 하나가 틀어지면 문서 전체의 신뢰가 무너집니다.

그래서 **추출부터 번역, 검수까지 전 과정을 로컬 GPU 서버에 올리고**, 연구진이 원문과 번역문을 블록 단위로 직접 대조할 수 있는 화면을 만들었습니다.

## 🔄 3단 파이프라인

```
PDF 업로드
   │
   ├─ ① MinerU ──────────── 레이아웃 인식 블록 추출
   │                        (본문 · 표 · 각주 구조 보존)
   │
   ├─ ② Gemma4 ──────────── 섹션별 문맥 생성 + 자료 유형 분류
   │                        1~2문장, 인명 제외
   │                        판결문 / 선례 / 변론서 / 증거 등 9종
   │
   └─ ③ TranslateGemma ──── 문맥을 함께 넣어 블록 단위 번역
                            sv → en / ko
   │
   ▼
블록 정렬 → 좌우 동기 스크롤 대조 화면 → 검수 → 다운로드
```

### ② 단계가 핵심입니다

블록 단위로 쪼개 번역하면 **앞뒤 맥락이 끊겨 용어가 흔들립니다.** 같은 단어가 문단마다 다르게 번역되는 문제입니다.

그래서 번역 전에 Gemma4가 해당 섹션의 문맥을 1~2문장으로 요약해 **번역 프롬프트에 함께 넣습니다.** 프롬프트는 "뒤따를 번역의 중의성 해소에 유용한 사실만" 쓰도록 지시하고, **인명은 넣지 않도록** 명시합니다.

동시에 그 섹션이 판결문인지 증거인지 변론서인지를 신뢰도 점수와 함께 분류해, 문서 종류에 맞는 번역 톤을 잡습니다.

## 🛡 번역 훼손 자동 검증

번역 과정에서 법률 식별자나 수치가 바뀌면 문서의 의미 자체가 달라집니다. 번역 결과를 그대로 받아들이지 않고 두 단계로 확인합니다.

| 검사 | 내용 |
|---|---|
| **식별자·수치 대조** | 사건번호 · 판례번호 · 금액 같은 값이 원문과 번역문에 **그대로 남아 있는지** 대조. 하나라도 달라지면 경고 |
| **분량 이상 감지** | 번역문 길이가 원문의 0.25~4배를 벗어나면 경고, 8배를 넘어서면 **번역을 반려하고 다시 돌립니다** |

식별자가 바뀐 경우는 번역을 멈추지 않고 **검수자에게 어디를 봐야 하는지 표시합니다.** 의미가 실제로 훼손됐는지는 사람이 판단합니다.

## 🖥 검수 화면

- **블록 단위 정렬** — 원문 블록과 번역 블록이 1:1로 붙습니다
- **좌우 동기 스크롤** — 한쪽을 내리면 반대쪽이 같은 위치를 따라갑니다
- **수정 이력** — 검수자가 고친 내용을 리비전으로 보관합니다
- **재시도** — 추출이 실패한 문서는 PDF를 다시 올리지 않고 그 자리에서 재실행합니다

## 🔐 접근 통제와 감사

비공개 문서를 다루는 시스템이라 **누가 무엇을 열어봤는지 남깁니다.**

- 초대 코드 기반 가입 + 세션 인증, Google 로그인 연동
- 프로젝트·문서 단위 소유권 관리
- 문서 열람·처리 이력을 `AuditEvent`로 기록, 관리자 화면에서 조회
- **감사 API 응답 필드를 화이트리스트로 제한** — 원문 텍스트·저장 경로·자격증명은 과거 기록에 남아 있어도 밖으로 나가지 않습니다
- 내부 서비스 URL은 loopback과 터널 호스트로만 허용 (`_validate_private_service_url`). 실수로 외부 주소를 넣으면 서버가 기동되지 않습니다

## ⚡ 공용 GPU 운용

모델이 올라간 GPU 서버를 여러 연구원이 함께 씁니다. 항상 띄워두면 다른 작업이 막히고, 매번 내리면 대기 시간이 길어집니다.

**요청이 있을 때만 필요한 모델을 기동하고, 유휴 상태가 이어지면 내리는** 방식으로 해결했습니다.

연구실 구성원이 GPU 서버에서 `litailab-reserve` 명령으로 예약 상태를 바꾸면 GPU 관리자가 그 상태를 유지합니다. 웹 백엔드는 명령을 직접 실행하지 않고 GPU 관리자 API를 조회합니다. 프론트엔드는 `/api/system/gpu-status` 결과를 약 5초 간격으로 받아 예약·모델 상태를 표시합니다.

- 작업이 큐에 들어오면 해당 모델만 기동
- 일정 시간 사용이 없으면 자동 종료
- 다른 연구원이 GPU를 예약하면 진행 중 작업이 끝난 뒤 모델을 내리고, 새 작업은 **실패시키지 않고 큐에 쌓아** 둡니다
- 관리자 화면에서 GPU 상태와 사용자 활동 로그 확인

## 검증 및 성과

MinerU 추출 → Gemma4 문맥 생성 → TranslateGemma 번역 → 원문 대조·검수로 이어지는 흐름을 구축하고 NAS Docker 환경에 배포했습니다. 실패 작업의 상태를 보관하고 재시도할 수 있도록 했습니다.

## 한계와 회고

번역 정확도·식별자 보존율·처리 속도의 정량 평가는 아직 없습니다. 문서 처리 모델은 자체 GPU 환경에서 실행하지만, 로그인 등 시스템 전체를 완전 오프라인이라고 설명하지 않습니다. 번역 모델만큼 추출 품질과 사람의 검수 흐름이 중요했습니다.
